# Configuration Proof


## 1. High Level Conclusion

```
Branch 1 (the slow path, for real proposals)
  ProposerSafe (5/11) --module--> Delay Modifier (+ PauseGuard) --module--> OwnerlessSafe --DEVOPS_ROLE--> Term Protocol

Branch 2 (the token-vote path, whose only power is to veto)
  Governor --module--> Roles Modifier (+ SetTxNonceGuard) --target--> DelayOwnerSafe --owner--> Delay Modifier

Pause controls
  PauseSafe (2/9) --pause-->               PauseGuard
  AdminSafe      --unpause / setPauser-->  PauseGuard
```


The conclusions drawn from these proofs establish the following propositions:

1. The Term multisig holders on the ProposerSafe and the Term multisig holders on the OwnerlessSafe, and only they, may execute DEVOPS_ROLE methods, holding: 1. the owners, fallbackHandler, modules, guard constant for the ProposerSafe and OwnerlessSafe, and 2. the owner, target, modules, guard, txCooldown, txExpiration constant for the Delay Modifier, and provided the DEVOPS_ROLE method call is not vetoed.

2. Only TERM token holders and Term multisig holders may veto Delay Modifier transactions, holding: 1. the owners, fallbackHandler, modules, guard constant for the DelayOwnerSafe, and 2. the owner, target, modules, guard constant for the Delay Modifier and Roles Modifier, and 3. the role targets, role scopes, role assignments constant for the Roles Modifier, and 4. the voting token, proposal threshold, voting threshold, quorum constant for the Governor.

3. The following: 1. the owner, target, modules, guard, role targets, role scopes, role assignments for the Roles Modifier, and 2. the voting token, proposal threshold, voting threshold, quorum for the Governor cannot be changed by anyone.

4. The following: 1. the owners, fallbackHandler, modules, guard for the ProposerSafe, OwnerlessSafe, and DelayOwnerSafe, and 2. the owner, target, modules, guard, txCooldown, txExpiration for the Delay Modifier can be changed only by the Term multisig holders on the ProposerSafe, OwnerlessSafe, or DelayOwnerSafe.

Only Term multisig holders can execute DEVOPS_ROLE methods subject to TERM token governance, and this cannot be changed other than through Term multisig approval.

## 2. Evidence Classification

This document uses two classes of evidence to establish the security and functional properties of the governance configuration:

- **Formal Verification (FV) evidence** establishes that, assuming the stated configuration, the relevant contracts enforce the claimed security and functional properties. These properties are proved with the Certora Prover, a formal verification tool. The proofs cover privileged entry points, authorized callers, configuration immutability, the absence of alternative execution paths, and the intended functionality. In the tables below, FV evidence is labeled **FV —** and names each Certora rule; ✅ marks a rule that passes.
- **Deployment evidence** establishes that the deployed contracts have the configuration assumed by the formal verification evidence. This includes on-chain verification of contract addresses, owners, modules, guards, thresholds, roles, and other relevant state, with each value read at a stated block. In the tables below, deployment evidence is labeled **On-chain —**; ✅ marks a read that matches the stated configuration.

These two classes of evidence are complementary. Formal verification evidence does not by itself establish that the deployed contracts have the configuration being proved, and deployment evidence does not by itself establish that the deployed configuration enforces the claimed security and functional properties.

Configuration items marked ⏳ (pending migration) describe the intended post-migration configuration and are not established by the current deployment evidence. These items must be re-verified against on-chain state after the migration is executed.

## Scope of the claims

These are compatibility proofs of the existing conditional models. Their assumptions remain visible in the pinned specifications:

- **Delay:** owner/module authority, queue provenance, pause behavior, signed settings and the existing composed Safe paths. The existing signature stubs, authorized-caller relations, scene links, guards, bounded queue/hash behavior and dispatch defaults remain.
- **Safe 1.3.0 and 1.4.1:** entry paths, self-calls, handler behavior, configuration guards, module behavior and signed settings. Existing signature summaries, configured guard/module/owner premises, external-call abstractions and recursion/loop bounds remain. Signed witnesses do not independently prove signature validation.
- **Roles:** guard sufficiency and whether the configured veto call lands on Delay. Guard installation, target/owner relations, role configuration, caller membership and bounded calldata assumptions are unchanged.
- **Governor:** proposal threshold, settings, vote accounting and tally stability. The linked TERM scene, historical-vote/signature summaries, external-call abstractions, optimistic hashing and loop bounds remain. These runs do not establish the correctness of every summarized external dependency.

The inventory accounts for 41 specs in 41 contexts and issues **zero semantic dependency-closure certificates**. Deployment bindings, abstraction refinement, specification adequacy and mutation coverage remain separate obligations. No negative-control proof is claimed in this batch.

## Diagnostics

The record distinguishes inherited diagnostics, diagnostics outside the exercised methods, and analysis whose optimization was already disabled. No analysis flag or scope filter was changed to silence a diagnostic.

- The six manual Safe/Delay comparisons retain the same `execTransaction` call-graph failure on **both uncached versions**, including signed paths. Their reported calls and full result coverage are preserved. Certora [falls back to another call-graph analysis](https://github.com/Certora/CertoraProver/blob/8.19.2/src/main/kotlin/analysis/icfg/CallGraphBuilder.kt#L4485-L4538). Other Safe contexts report it only for unexercised `execTransaction`; that exclusion is checked against the actual method instances, specs and reported calls.
- Safe `getStorageAt` storage-analysis/splitting diagnostics concern an unexercised method. Governor scenes also retain an internal-function detection diagnostic in TERM's unexercised `send`. No method or contract was removed from the compiled scene.
- Governor voting's five active voting methods report the same storage-analysis/splitting failures in its **fresh 7.31.0 baseline and 8.19.2 candidate**. Both complete successfully with identical compiled methods and reported calls. The spec uses Solidity getters and contains no CVL storage hooks. Governor settings already disables storage splitting on both versions and also has no storage hooks. The [storage-analysis implementation retains a failure only for later consumers](https://github.com/Certora/CertoraProver/blob/8.19.2/src/main/kotlin/analysis/storage/StorageAnalysis.kt#L4195-L4203), and [storage-splitting failures can affect runtime](https://github.com/Certora/CertoraProver/blob/8.19.2/src/main/kotlin/analysis/split/StorageSplitter.kt#L71-L90). These are recorded limitations, not clean analysis logs.
- Call-trace argument-display errors remain in some suites. Governor settings' old cached baseline has one verified sanity result whose trace generation failed; the 8.19.2 candidate has no report-node errors. Thousands of older display-annotation warnings are absent on 8.x. These reporting improvements do not discharge semantic-closure obligations.

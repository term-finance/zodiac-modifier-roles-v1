# Remaining Roles migration: packed permission keys

The migration remains at **40 of 41 existing configurations**. `Roles-setTxNonceGuardAndRoleConfig.conf` stays on 7.31.0. The October 14 experiments below do not establish a valid configuration for moving it to 8.19.2. They identify a reproducible difference between native EVM execution and the prover model, and a separate internal error with precise memory enabled. They do not establish that a prover source change is the only possible solution.

The [experiment record](8.19.2-packed-keys.json) includes every submitted variant, its completion state, input hashes, report URL, result counts and retained archive hash. Incomplete jobs are explicitly excluded from successful evidence. Access tokens and signed download links are omitted. The previous [migration record](8.19.2-second-batch.md#remaining-on-7310) retains the fresh 7.x comparison and its two library-call havoc warnings.

## Native behavior and the discrepancy

The source is pinned at [`b1b6439`](https://github.com/term-finance/zodiac-modifier-roles-v1/tree/b1b643961147b202d0d5d9bf16c0475d548ce58d). [`Permissions.keyForFunctions`](https://github.com/term-finance/zodiac-modifier-roles-v1/blob/b1b643961147b202d0d5d9bf16c0475d548ce58d/packages/evm/contracts/Permissions.sol#L958-L964) packs a 20-byte address, a four-byte selector and eight trailing zero bytes. Numerically, the result is `address * 2^96 + selector * 2^64`. Both [existing scope getters](https://github.com/term-finance/zodiac-modifier-roles-v1/blob/b1b643961147b202d0d5d9bf16c0475d548ce58d/packages/evm/certora/harness/RolesHarness.sol#L59-L81) use this library function to select the permission-map entry.

For target zero and selector `0x00000002`, native Solidity 0.8.6 bytecode returns `0x0000000000000000000000000000000000000000000000020000000000000000`. A default 8.19.2 diagnostic instead returns zero. The earlier full-suite witness also loses the selector contribution, for target `0x2546` and selector `0x46ba2307`. These observations concern the computed key, including its pre-solver expression, rather than only a call-trace display.

The [native replay](../check-packed-function-keys.cjs) compiles the unchanged harness and library, derives the mapping location from the compiler's storage layout, writes an independently constructed packed-key entry, and calls both getters. It checks 168 cases per compiler setting: calldata lengths 0–5, 31, 32, 35–37, 64, 96 and 257; zero, all-ones, veto-selector and deterministic mixed bytes; zero, small and maximum addresses; and roles 0, 1 and 65535. It also replays five distinct library-call argument pairs from the diagnostic counterexamples.

All checks pass with Certora's default disabled-inliner setting, the standard optimizer, and optimization disabled: **504 getter cases, 1,008 getter calls and 15 library-call replays**. The EVM and compiler target Berlin. These are finite native checks and library-call replays, not universal proofs or replays of entire CVL transaction states. No contract defect was reproduced.

## Arithmetic key candidate: local evidence only

The next isolated experiment replaces the two pure packed-key functions with arithmetic models, after separately checking their return values against the unchanged library. `keyForFunctions` is `address << 96 | selector << 64`; [`keyForCompValues`](https://github.com/term-finance/zodiac-modifier-roles-v1/blob/b1b643961147b202d0d5d9bf16c0475d548ce58d/packages/evm/contracts/Permissions.sol#L966-L974) additionally places `uint8(index)` at bit 56. No production Solidity is changed. These are explicitly candidate summaries, not harness implementations of the real functions.

Halmos 0.3.3 checked both functions on Solidity 0.8.6 bytecode with arbitrary addresses, selectors and indices, under the three optimizer settings used above. All six checks pass, with normal return paths, no blocked paths and no exhausted loop bounds. The [value lemma](packed-key-value-lemma.sol) asserts that both static calls succeed, compares their results, and independently checks each output field and trailing zero bits. It uses no input assumptions. Erasing the selector only in the model makes both symbolic checks fail; both counterexamples also reproduce on the native EVM under all three compiler settings. Separately, 576 finite native cases match the correct model and preserve storage. The [local evidence record](8.19.2-key-model-candidate.json) binds these results to compiler settings, tool versions, source hashes and retained artifact hashes.

This proves a narrower claim than the proposed internal summaries require. The original `abi.encodePacked` allocates memory; an internal caller can share that memory, whereas the standalone wrappers call the library externally. Return equality and storage frames alone do not establish preservation of observable caller-memory behavior. That obligation remains open, particularly around the library's assembly parsing. The candidate is not approved or adopted, and the local results do not count as a Certora 8 full-suite pass.

Three separate patches apply to the same pinned base commit; do not combine them:

- [Value-equivalence diagnostic](packed-key-model-equivalence.patch): real library versus candidate, independent expected values and storage frames, without summaries or new input restrictions. The loop setting is pessimistic.
- [Negative control](packed-key-model-negative-control.patch): the same diagnostic with the selector removed only from the candidate. The real library remains unchanged.
- [Full-suite candidate](packed-key-model-full-suite.patch): two internal rerouting summaries, all original rules and preconditions, and the actual-getter storage-key regressions. It uses precise bitwise operations without precise memory flags. Its original optimistic loop bound remains.

All three compile locally with CLI 8.19.2. None has been submitted to Certora cloud. Upload authorization is pending. Even successful cloud results would still require resolving the internal-memory obligation, checking that the summaries attach as intended, and approving the changed assumptions before promotion.

To reproduce the local symbolic checks, apply the value-equivalence patch in a separate checkout, copy `packed-key-value-lemma.sol` from this PR into that checkout as `packages/evm/certora/lemmas/PackedKeyEquivalence.t.sol`, and create this `foundry.toml` in `packages/evm`:

```toml
[profile.default]
src = "certora/lemmas"
test = "certora/lemmas"
solc = "0.8.6"
evm_version = "berlin"
optimizer = true
optimizer_runs = 1
dynamic_test_linking = false
remappings = ["@gnosis.pm/=node_modules/@gnosis.pm/"]

[profile.default.optimizer_details]
inliner = false
```

Then run Halmos 0.3.3 with Z3 4.12.6 and Foundry 1.8.5 from `packages/evm`:

```sh
halmos --contract PackedKeyEquivalenceLemma --storage-layout generic \
  --solver-command z3 --solver-timeout-assertion 120s \
  --solver-timeout-branching 100ms --loop 16 --panic-error-codes '*' \
  --json-output result.json --dump-smt-queries \
  --dump-smt-directory smt --statistics --no-status
```

For the standard optimizer, omit the `optimizer_details` table; for the unoptimized case, also set `optimizer = false`. Use the negative-control patch in another checkout to reproduce the two expected failures. The scalar-only lemmas require no array-length restrictions; the loop bound is recorded even though no paths exhaust it. These checks do not compare gas or internal caller memory.

## Reproduce

From `packages/evm`, with the locked dependencies installed and Solidity 0.8.6 available:

```sh
SOLC_BINARY=solc8.6 node certora/check-packed-function-keys.cjs /tmp/packed-keys.json
```

CI executes this native check once in the existing held-back Roles matrix job, before the cloud proof. It uses no RPC, signer or cloud credential. The script also records source and runtime hashes when given an output path. Passing this native check alone does not validate Certora's model.

For cloud reproduction, apply exactly one supplied patch with `git apply --unidiff-zero` to a separate clean checkout of `b1b6439`. The zero-context patches preserve the exact submitted source bytes:

- [packed-key-diagnostic.patch](packed-key-diagnostic.patch) selects the two key diagnostics and exposes the real library through two harness getters. It contains no new `require`, axiom or summary. It intentionally does not run the original functional rules.
- [packed-key-full-suite.patch](packed-key-full-suite.patch) retains every original rule, adds observational storage-key regressions, and enables precise memory/bitwise settings. No Solidity file changes. The original preconditions, summaries, method filter, links and loop bound remain.

Then, from that checkout's `packages/evm`:

```sh
pip install -r requirements-8.txt
certoraRun certora/confs/Roles-setTxNonceGuardAndRoleConfig.conf \
  --solc solc8.6 --rule_sanity basic \
  --disable_auto_cache_key_gen --wait_for_results all
```

Provide `CERTORAKEY` through the environment. To reproduce the passing isolated diagnostic, use the first patch and add `--precise_bitwise_ops --prover_args '-smt_preciseBytemaps true -exactByteMaps true'` to that command. The full-suite patch already contains its tested flags. Both the single-string form and separate quoted options pass local compilation with CLI 8.19.2.

## Acceptance and limits

A future promotion must pass the full original suite, the successful-call witness and every sanity result while preserving the actual packed keys. A green job with a different key, an incomplete job, or a diagnostic-only success is insufficient. These experiments retain the existing optimistic loop bound of one; the finite native cases do not remove that limitation. The maximum arithmetic result in the added key assertions is below `2^256`, including with precise bitwise operations' [documented integer restriction](https://docs.certora.com/en/latest/docs/prover/cli/options.html#precise-bitwise-ops).

The checked-in proof configurations, Solidity, harnesses, CVL and CLI routing are unchanged. No replacement summary or new proof assumption is adopted. The model discrepancy concerns a shared library, so the earlier 8.x compatibility passes must not be read as universal validation of that library's semantics. The existing 41-context inventory still issues zero semantic dependency-closure certificates. No deployed-bytecode binding, unbounded-loop claim, complete specification-adequacy claim or deployment change is established here.
